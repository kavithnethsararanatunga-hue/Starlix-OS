# Starlix OS 1.0 Beta — RXFS Runtime Phase 1

## Scope

This phase adds the first kernel-side, read-only RXFS v1.0 runtime volume reader. It reuses the existing EHCI USB Mass Storage block-device layer and does not add filesystem write operations. Existing FAT32 behavior is retained.

This is a storage/path foundation only. It does **not** implement user-mode execution, an ECT loader, `.app` parsing, GUI startup, authentication, or the lock screen.

## Public interfaces

`kernel/src/rxfs_native.hpp` provides a callback-based reader that can also be host-tested independently:

- `MountNativeRxfs(...)` — validate boot sector, superblock, UUID relationship, and volume bounds.
- `LookupNativeRxfsPath(...)` — resolve a path to `NativeRxfsNode` metadata.
- `ReadNativeRxfsFile(...)` — read a regular file into a caller-provided buffer.

`kernel/src/storage/storage.hpp` exposes the storage integration:

- `rxfs_volume_count()` / `rxfs_volume_get(...)`
- `rxfs_mount(...)`
- `rxfs_lookup_path(...)`
- `rxfs_read_file(...)`

The storage adapter translates the device's supported logical block size (512, 1024, 2048, or 4096 bytes) into RXFS 4096-byte blocks. It bounds-checks every request against both the selected partition and the physical device.

## Discovery and path behavior

After EHCI mass-storage initialization, `storage_init()` tries RXFS on discovered MBR/GPT partitions regardless of their partition type, then retains the existing FAT32 detection path. It also supports whole-disk RXFS images without a partition table. Storage remains read-only for RXFS.

Paths may use `/` or `\\` separators and may optionally start with an `RXFS` volume prefix. Examples:

```text
RXFS\\sys\\User\\smgrsb.ect
RXFS\\sys\\User\\stitzn.ect
RXFS\\sys\\User\\lsass.ect
RXFS\\sys\\User\\stlgn.ect
RXFS\\Applications\\Explorer.app\\Contents\\config.plist
RXFS\\Applications\\Explorer.app\\Contents\\explorer.ect
RXFS\\Applications\\Explorer.app\\Contents\\Resources\\icon.png
```

A `..` path component is rejected. Directory lookup validates record lengths, filename lengths, inode references, and inode checksums. File reads validate inode checksums and block addresses before reading.

## Supported RXFS subset and current limits

- RXFS version 1.0-compatible superblocks with no required or read-only-compatible features set.
- Regular files and directories.
- Twelve direct data-block pointers plus one single-indirect block table (512 64-bit entries): at most 524 data blocks, approximately 2.05 MiB per file or directory.
- Uncompressed, unencrypted, non-sparse file data.
- Directories stored as ordinary file data blocks.
- CRC32C validation for the superblock and each inode read.

The reader intentionally rejects double/triple-indirect pointers, extent trees, B-tree directories, compression, encryption, sparse files, deduplication, reflinks, unsupported feature flags, invalid block pointers, and malformed directory records. It does not yet implement symlinks, case-folding, ACL enforcement, xattrs, file-data checksum trees, journaling/recovery, or write operations.

## Build and host validation

From the project root:

```bash
bash scripts/build_kernel.sh
bash scripts/build.sh
bash tests/test_rxfs_native.sh /path/to/mkfs-generated.rxfs
```

The host self-test constructs a synthetic RXFS volume containing the planned `sys/User` components and an `Applications/Explorer.app/Contents` bundle. It also accepts an optional image generated by the project's `rxfs/tools/mkfs.rxfs` formatter.

## Next phase dependencies

Before `smgrsb.ect`, `stitzn.ect`, `lsass.ect`, `stlgn.ect`, or `Explorer.app` can execute, Starlix still needs a real user-mode execution foundation: protected user address spaces, a working Ring 3 transition and return path, syscall validation, process/thread scheduling, IPC/service lifecycle, and an ECT loader with bounds and signature/format checks. This Phase 1 reader only makes RXFS file contents available to kernel callers; it does not make those files executable.
